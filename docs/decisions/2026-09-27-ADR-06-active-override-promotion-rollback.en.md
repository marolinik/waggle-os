## §2 — Decision (contract proposal)

**ADR-06-O1 (PROPOSAL) — one resolver, custom/override wins by id.** `listPersonas()` returns a `Map` keyed by `id` in which the override/custom **replaces** the built-in (custom last); `resolvePersona` in chat/fleet/agent-groups uses that resolver; the baseline endpoints (`routes/evolution.ts:259`, `evolution-service.ts:277`) use the same resolver (the active version, not the built-in). This does not break `personas.test.ts:43-47` (23 entries without dataDir; `not.toBe(PERSONAS)` holds) or `personas-routes.test.ts:121-140`.

**ADR-06-O2 (PROPOSAL) — active-version registry (A2, A18).** For each target (`persona-system-prompt:<id>`, `behavioral-spec-section:<name>`, later `skill-body`, `recipe`): versioned records `{versionId, targetKey, content, sourceRunId?, createdAt, activeFrom?, activeUntil?}` + **one** active pointer per target. Interim implementation without a new database: `evolution_runs` gets `active_from/active_until`, the override file remains a materialized projection of the active version; `.bak` is replaced by a multi-level history (previous versions are rows, not a file). Migration: existing `<id>.json` override + `.bak` → two versions (active + previous).

**ADR-06-O3 (PROPOSAL) — activation is a check, not a write (DIR-13, AT-04).** `markDeployed` only after the activation check: the resolver returns the written content (`resolvePersona(id).systemPrompt === override`); otherwise status `written_not_active` with a reason. Order: O1 before O3 (otherwise `evolution-routes.test.ts:169-188` fails). UI copy per target kind: "Accept & Activate"; "deployed lift" only when the gate is paired (O5); fix `docs/…/05d-subsystem-evolution.md:5,94`. `systemPromptCache.clear()` on `persona:reloaded`/`behavioral-spec:reloaded` (optional, the key already contains `historyLength`); the WS relay forwards evolution events so that the UI learns of them.

**ADR-06-O4 (PROPOSAL) — rollback and pinning.** `POST /api/evolution/runs/:uuid/rollback` calls the existing `rollback*Override` + moves the active pointer to the previous version; new status `rolled_back` (migration of the `CHECK` in `evolution_runs` — SQLite table-rebuild). Rollback changes the **next** run; an already started `DurableRun` stays on the `recipe/persona version` pinned in the run (ADR-02 O1; precedent: fleet persona snapshot `fleet-run-executor.ts:589-591`, test `fleet-isolation.test.ts:455-485`). A code rollback does not restore deleted data or revoked consents (DIR-21).

**ADR-06-O5 (PROPOSAL) — promotion policy object (A18, DIR-15).** Persisted with each version: `{holdoutHash, nExamples, pairedMetric, effectEstimate, ciLowerBound, minPracticalDelta, perShapeRegressionFloor, costLatencyCeiling, graderErrorPolicy, holdoutViews}`. Rules: the baseline and the candidate are **always** re-scored on the **same** holdout set and budget (the anchor phase also scores the baseline — a separate `anchorScore` field, not an overwrite of the micro score); `combinedDelta` remains as a field (test) but is **renamed in the UI** / not used for the gate; errors do not drop out of the denominator (`aggregateScores` returns `n_failed`, `n_aborted`; infra error ≠ model failure); a metric-appropriate interval, not a universal McNemar/TOST; "≥30" is not evidence of sufficient power — N and the margin are chosen before the test (brief §10.5); repeated views of the holdout are recorded and limited. The first promotions are explicit (`EvolutionService` already produces only `proposed`, never auto-deploy); automatic promotion = a separate policy after evidence.

**ADR-06-O6 (PROPOSAL) — dataset governance (A17, AT-29, AT-13, AT-19).** The orchestrator uses `builder.build({traceFilter:{personaId, workspaceId}, includeCorrections:false, seed})` (secret scan, dedup, split); a correction is a **signal**, not gold; every example carries `provenance/scope/qualification`; personal work does not spill over into a shared set without permission (KVARK: ADR-08); `positiveOutcomes` excludes `gate_passed`/legacy `verified` until there is a `ProofReceipt` (ADR-01 O5). GEPA phases run on `train+val`, the final paired score on `holdout`; `artifacts` records `datasetHash`, `holdoutViews`, `executorModel`, `judgeModel`, and redacted per-example outputs.

**ADR-06-O7 (PROPOSAL) — executor through the target runtime; judge independence desirable, not mandatory (A19 AMEND THE ABSOLUTE CONDITION).** An `EvolutionLLM` adapter over the existing provider router / the selected local model (the `complete(prompt)` contract remains); the candidate is executed with the **composed** system prompt (`composePersonaPrompt(core, {systemPrompt: candidate})`), not as a single user turn; the local evaluator is the default for the local profile; the same local model may be both generator and rubric evaluator in separate roles, with an **explicitly flagged bias risk** in the run artifact; a different model family is the recommended control; final quality evidence is deterministic or comes from independent/human review per the protocol (ADR-01 O5 levels).

**ADR-06-O8 (PROPOSAL) — privacy and cost (A16, D-03, D-05).** A cloud/BYOK judge requires per-run `consent` (what is sent, minimization/redaction, budget) — not the legacy Anthropic-key condition; pre-run cost estimate, hard cap (`maxJudgeCalls`/`maxCostUsd`), abort tied to `request.raw.on('close')` is **optional** (the run may continue detached per ADR-03, but the user must have an explicit Stop); in KVARK mode a cloud judge is not available (ADR-08). The evaluator cost counts toward the run budget (ADR-02 O7).

**ADR-06-O9 (PROPOSAL) — EvolveSchema: wire it or drop it from the default compose (R19).** Decision by test: pass `frozenSchema` into the Stage 2 executor (the schema-fill part of the prompt) and into the deploy artifact, then measure the effect on the paired holdout; if there is no measurable effect → Stage 1 is taken out of the default compose (it remains as opt-in), without renaming it to "evolves the entire way of working".

**ADR-06-O10 (PROPOSAL) — learning: one channel, not two (R18, C10).** Keep the existing path `analyzeAndRecordCorrection → improvement_signals → # User Corrections`; add only (a) `traceRecorder.markCorrected(prevTraceId)` when `detectCorrection` hits (so that the eval set sees `corrected`), (b) a persona signal from `finalizeOnce` if persona-effectiveness is retained as a requirement, (c) resolve the `markSurfaced` semantics (UNKNOWN who calls it). `AgentLearning.formatLearningPrompt` and `improvement-wiring.ts`: **remove** (remove the export `index.ts:231`, rephrase PRD §9) unless the founder keeps persona-effectiveness — in that case, wire it through the same signal channel, without a second prompt block.

**ADR-06-O11 (PROPOSAL) — bounded recipe evolution (DIR-14) is a separate scope.** A registry of approved variants for research/document (e.g. the base procedure ± contradiction check ± a permitted retrieval/review variant); candidates change the instructions, the arrangement of approved optional phases, and budgets within the limit. Invariants: scope, egress prohibitions, approvals, budget cap, mandatory gates, contamination boundary, meaning of success. A recipe that wins by skipping a safety check is not a candidate. It is **not** included in S1 W3e; the planner estimates it separately; if it is deferred, show which user outcome/public claim drops out (brief §10.3).
