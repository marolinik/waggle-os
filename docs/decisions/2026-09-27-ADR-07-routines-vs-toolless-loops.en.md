## §1 — Context

**ADR-07-K1 (HISTORICAL FOUNDER DECISION — memory `project_loops_feature_decisions.md`, 2026-06-29 — aligned with D-01 (Loops free) and brief §11.5/C15 (L2 TOOLLESS); not a D authority per brief §2.1).** Two settled decisions: (1) **all Loops are free** — L1 report-only and L2 assist remain without a tier gate; (2) **L2 stays TOOLLESS (v0)** — the maker is a plain text completion that proposes **one** action through a fenced ```json block, which is held in the held queue; the "v1" path (tool-enabled agent loop in the scheduler with a headless `ConfirmationGate` → queue) is **deliberately deferred**, with a recorded "chaining limitation" (when a human approves later, the run that proposed it has already finished). This ADR reopens neither of those decisions.

**ADR-07-K2 (DECISION — D-14 · PROPOSAL — BRIEF DIRECTION — DIR-19, C15 CARVE-OUT, R05, R10).** DECISION: long-running work and routines are part of the product; a switched-off laptop does not execute local work (D-14). PROPOSAL — BRIEF DIRECTION (planner direction, not user approval): "A trigger is not new intelligence" (DIR-19): a routine is a schedule/event trigger for a permitted work recipe, with its own occurrence identity, budget, Workspace, policy and result channel; there is no separate "routine harness family" (R05); the existing `CronStore`/`LocalScheduler` and management UI are the first candidates for reuse. The old TOOLLESS Loop remains detection/proposal within its constraint (founder decision, K1); an approved routine may start a tool-using work run **through the same permission/durable layer** (C15 CARVE-OUT) — this requires an explicit demarcation (this ADR), not a silent expansion of the old loop's authority.

## §2 — Decision (contract proposal)

**ADR-07-O1 (PROPOSAL) — two contracts, one terminology.**

| Term | What it is | What it may do | What it must not do | Today |
|---|---|---|---|---|
| **Loop L1** | scheduled toolless report grounded in memory | read the mind (recall), write a report frame into its **own** mind, notify | call a tool, send, write a file | `job_type:'loop'`, `mode:'report'` |
| **Loop L2 (assist)** | L1 + **one** action proposal | everything from L1 + `enqueueHeldAction` (held, validated at the boundary) | execute the action; propose more than one; use the result of action N for N+1 (chaining limitation remains) | `mode:'assist'` |
| **Routine** | schedule/event **trigger** that creates a `DurableRun` with `interaction:'work'`, a chosen recipe and an **occurrence identity** | everything that recipe may do under the permission envelope (ADR-04 O5); tool-using phases; `BLOCKED_APPROVAL`/`BLOCKED_CAPABILITY` as a run state; resume after approval in the **same** run | silent acquisition (installation/OAuth without the user); sending without a separately approved `ToolAction`; inheriting a scope wider than the recipe's | closest ancestor: `agent_task` + `mode:'ai_task'` (K4) |

A Loop is **not** turned into a Routine by renaming; a Routine does **not** use the Loop maker. "Routine" in UI copy covers all three (the user sees one Home block), while the contract underneath distinguishes `kind: 'loop_report' | 'loop_assist' | 'routine_work'`.

**ADR-07-O2 (PROPOSAL) — a Routine is a trigger, not an executor (DIR-19).** `RoutineDefinition { routineId, workspaceId, recipeId/recipeVersion, schedule { cronExpr, timezone }, misfirePolicy, budgetPerOccurrence, permissionEnvelopeRef, resultChannel[], enabled }`. The tick **does not execute the work**: it creates `RoutineOccurrence { occurrenceId, routineId, scheduledFor, firedAt, runId?, outcome, leaseOwner, fenceToken, spent }` and **one** `DurableRun` (ADR-02 O2 ordering: run before side effect). The executor signature receives the occurrence (`JobExecutor(schedule, occurrence)` — additive; `cron.ts:19`). The recipe is the same as for manually started work (W3 two recipe paths); the routine adds no phases.

**ADR-07-O3 (PROPOSAL) — occurrence identity and no duplicate actions (AT-23, AT-08; brief §6.5).** Every approved occurrence of a routine has its own `occurrenceId` → every external action of that occurrence is a separate `ToolAction` (`actionId`, ADR-02 O5): two daily routines legitimately send two similar reports; the **same** occurrence after a crash must not produce a second action: dedup by `(occurrenceId, tool, argsFingerprint)` while an `unknown_outcome`/`dispatching` exists. For legacy `ai_task` until W1: `sweepInterruptedRuns` moves `next_run_at` to the next slot **or** requires `job_config.rerunAfterInterrupt` before re-execution (F-DUR-10 "smallest change (b)").

**ADR-07-O4 (PROPOSAL) — misfire, timezone, DST, restart (brief §11.5).**
- `misfirePolicy: 'skip' | 'catch_up_once'` per routine; default = **the documented current implicit policy** (`catch_up_once` + retry-every-tick + 5-strike disable) until the founder chooses (MDQ-03 in MIG-02). Catching up again after sleep **never** turns multiple missed slots into multiple executions; one execution carries the `scheduledFor` of the first missed slot and the list of missed slots.
- `timezone` field (IANA) per routine; `null` = process local time zone (current behavior) — schema extension, additive (`cron_schedules` v2, MIG-02).
- DST: explicit test (transition 29.03./25.10. for `Europe/Belgrade`) — UNKNOWN today; policy: non-existent local hour → next valid one; duplicated hour → once.
- Restart: an occurrence with a live lease of the old process → fencing (ADR-02 O6): conditional claim (`INSERT … WHERE NOT EXISTS` / `UPDATE … WHERE leaseOwner IS NULL OR leaseUntil < now`), fence token in side-effect calls; `acquireRunLease` stops being a plain `INSERT`.
- Due-ness: **first** resolve K7 (W0-PR14): if confirmed, normalize the write format (`strftime`-compatible) or the comparison; only then define "missed slot".

**ADR-07-O5 (PROPOSAL) — occurrence budget (A10).** `RoutineOccurrence.spent` + `DurableRun.budget` (ADR-02 O7); a restart does not reset it; `AI_TASK_DAILY_CAP=24` **remains** as the upper bound per routine/day (UTC) with the skip reason explicitly shown in history; the Loop cost floor (`minIntervalMs`, `loop-executor.ts:224-230`) remains.

**ADR-07-O6 (PROPOSAL) — approvals (brief §11.5 "approval of a draft is not approval to send").** Approval of the **routine** (enable) ≠ approval of the **action**: sending/writing outside the Workspace is always a `ToolAction` under the envelope — held/`BLOCKED_APPROVAL` per the `ALWAYS_CONFIRM`/autonomy rules (ADR-04 O7); there is no "pre-approve all future actions of the routine" except an explicit grant per `keyForTool` (`ApprovalGrantStore`), which is visible and revocable. Chaining: for a `routine_work` run, a later approval does **not** execute the action standalone — the run is in `BLOCKED_APPROVAL` and continues after the grant (ADR-02 O2 step 6) → the "headless tick cannot wait for hours" premise from K1 holds for Loop, **not** for Routine (durable). For the L2 Loop, execute-on-approve from `held-action-executor.ts` remains (ADR-02 O5 status model).

**ADR-07-O7 (PROPOSAL) — Loop cross-tick state moves from Awareness to the execution store (brief §8.2; MIG-02).** `routine_state(schedule_id, last_result, last_tick_at, score)`; the Awareness row `status LIKE 'loop:%'` is removed (with a receipt); the report frame **remains** (derived memory, ADR-05 O1). Interim (before W1): a retrieval exclusion for `loop:` items would touch `toContext()` in the OSS substrate — **do not do this**, go directly to the move (W1-PR10).

**ADR-07-O8 (PROPOSAL) — Loops remain free and outside the tier gate (K1 enforcement; ADR-08).** No `assertTierCapability` on `case 'loop'` nor on `mode:'assist'` (grep `assertTierCapability` in `index.ts` = 0 relevant — CONFIRMED AT REVISION that the gate does not exist). Routine runs are also not behind a paywall (D-01).

**ADR-07-O9 (PROPOSAL) — UI without a new surface (DIR-16, R05).** Home gets a Routines block that reads the existing `/api/automations` (`HomeCockpit.tsx` panel grouping; F-UXM-13); `AutomationCenterApp` remains the management surface; `toAutomation` gets a derived `status: 'blocked'` when a held action with `source = loop:<id>` or a run in `BLOCKED_*` for the `routineId` exists, and when the last history row is `failed_interrupted`/rate-limited; the dead `'running'|'failed'` branches are either populated from lease/history or removed. The user sees the next slot (in `timezone`), the last result, the block, and pause/disable of the routine; pause/disable of the routine **is not** a mid-phase pause of the executor (`PAUSED` DEFERRED, ADR-02 O3).

**ADR-07-O10 (PROPOSAL) — what remains deferred.** New specialized families (meeting/routine harness, R05); the "v1 tool-enabled Loop" from K1 (not needed: Routine covers it under a different contract); mid-phase pause/backoff (R10); Waggle relay for routines when the desktop is switched off (brief §11.6). If Routine as a DurableRun is deferred past G2, show which user outcome drops out: "a routine that completes work with evidence" remains `ai_task` without checkpoint/occurrence (G2 minimum: no duplicate catch-up, plus lease fencing; G3 full: timezone/misfire UI — Delivery plan TM-07).
