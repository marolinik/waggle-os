### FRD-02.2 — `PhaseAttempt` — PROPOSAL

`{ runId, phaseId, attemptNo, inputRefs[], startedAt, endedAt, observedToolCalls[] (server ledger), artifactRefs[], gateResults[], verdict?, endReason: 'gates_passed' | 'gates_failed' | 'aborted' | 'budget_stop' | 'cancelled' | 'crashed' | 'skipped_by_policy' }`.
- `observedToolCalls` are populated **exclusively** from the server ledger (`chat-agent-run.ts:214-225 onToolResult`, `TurnToolActivity`), not from `phase_output.tool_calls` (F-HARN-08, DIR-07). Transitionally: mark the existing `PhaseOutput.toolCalls` as `selfReported: true`. In `strict` and `benchmark` the gate rejects self-reported evidence → `FAIL`. In `work · normal` a gate that is not a test/build gate transitionally accepts it as evidence, with the marker `selfReported: true` in the state; the outcome is then determined by the gate verdict per rows N1–N8 (FRD-05.9 R3).
- Exception to the transitional rule: the test/build gate (FRD-05.2, "Validator invocation") never accepts self-reported evidence, not even in `normal` mode. Its only evidence is the server record `ValidatorInvocation` in `observedToolCalls[]` — PROPOSAL (H-08, 30.09.2026).
- `skipped_by_policy` is allowed **only** in `work · normal`, as an explicit verify opt-out with a reason (FRD-05.9 R5); it yields `COMPLETED` only with `ProofReceipt.verdict:'NOT_RUN'` and the label "Completed (verify skipped)" (FRD-05.9 row N8). In `strict` and `benchmark` it does not exist; a skip without an explicit opt-out is a mandatory `NOT_RUN` and the run is not `COMPLETED` (F-HARN-01: currently `getRunSummary` writes `**Status:** Completed` alongside `| Verify | SKIP |`).
- Map to the existing `PhaseStatus` (`workflow-harness.ts:23`): `pending|active|validating|passed|failed|skipped` → `PhaseAttempt` is an instance of an attempt; `skipped` becomes `endReason: 'skipped_by_policy'` + `verdict: null`.

### FRD-02.6 — `ProofReceipt` — PROPOSAL (brief §7.2, three levels)

```
ProofReceipt {
  receiptId, runId, subject: { kind: 'artifact'|'phase'|'run', ref },
  level: 'structural' | 'defined_elements' | 'content_review' | null,   // null: nijedan nivo nije u celini potvrđen (FRD-05.9 R7)
  verifierVersions: { validators: Record<name, version>, grader?: { model, version, promptHash } },
  observedEvidence: EvidenceRef[],           // iz server ledger-a / validatora
  mandatoryGates: GateOutcome[], optionalGates: GateOutcome[],   // GateOutcome: FRD-05.9 R3
  verdict: 'PASS' | 'CONDITIONAL' | 'FAIL' | 'NOT_RUN',
  warnings[], unresolved[],
  qualification: 'qualified' | 'legacy_unqualified',
  createdAt
}
```
- **Not a general seal of truthfulness.** Level 1 confirms that the DOCX exists/parses/has sections and that a tool finished with an observed status — not that the conclusions are correct. Level 2 confirms amounts/dates/citations/references against the designated sources. Level 3 is a rubric for completeness/faithfulness — not a mathematical guarantee (brief §7.2).
- `COMPLETED` in `strict` and `benchmark` mode requires a receipt in which all `mandatoryGates` have `PASS`. A `CONDITIONAL` of a mandatory gate counts as `PASS` only per FRD-05.9 R4; no `conditionalPolicy`, user review or opt-out replaces that. In `normal` the only permitted exceptions are rows N3 and N8 of table FRD-05.9. The overall `verdict` and `level` are computed per FRD-05.9 R6/R7.
- Map to `TraceOutcome` (`execution-traces.ts:20`: `success|corrected|abandoned|verified|pending`): `verified` is currently written only by `HarnessTraceBridge`, for **every** completed phase (`harness-trace-bridge.ts:91`) — CONFIRMED AT REVISION (F-HARN-06, F-EVO-12). v1.2: a completed phase = `gate_passed` (structural), `verified` reserved for a receipt of level ≥2 with `verdict:'PASS'` (FRD-05.9 R8). **Warning from the refute pass:** `outcome` has an SQL `CHECK` in two places (`execution-traces.ts:150-151`, `mind/schema.ts:242-243`) → adding `gate_passed` is a table-rebuild migration (§14), not a type edit; the alternative without a schema change = `tags[]` + eval filter — PROPOSAL, a decision for the ADR authors.

**Validator invocation — contract for the test/build gate — PROPOSAL (H-08, 30.09.2026; DIR-07, A5; F-HARN-03, F-HARN-08)**

Validation status ("tests passed", "typecheck passed") arises only from a structured, server-observed call of an approved validator. The model, the command text and the output text cannot produce it. This is **not** a universal shell interpreter: the server does not interpret quotes, operators, variables, subshells, scripts or the contents of `package.json`. A call that is not literally equal to an approved validator does not qualify.

`ValidatorInvocation { validatorId, executor, argv[], cwd, startedAt, endedAt, exitCode: number | null, timedOut, background, executorError: string | null, resultFormat, parsed?: { total, failed, skipped }, observedCallRef }`. It is written exclusively by the server tool executor into the ledger `PhaseAttempt.observedToolCalls[]` (FRD-02.2); in G1 through the `observedToolCalls(sinceMarker)` provider (W0-PR8). The executor hands over these fields in structured form. They are never read from `phase_output.tool_calls` nor by parsing the tool result text.

- **VI-1 — approved validators.** The recipe/harness version declares `approvedValidators: [{ validatorId, argv[], resultFormat: 'exit_code' | <format parsera>, timeoutMs? }]`. G1 list for `code-review-fix` (PROPOSAL; changed only by a reviewed PR of the Harness owner): `npm test`, `npm run test`, `pnpm test`, `yarn test`, `npm run typecheck`, `pytest`, `python -m pytest`, `cargo test`, all with `resultFormat:'exit_code'`. `npx …` forms are not on the list: `npx` without a TTY can download and run a package that is not in the project. Extending the list per workspace or user: DEFERRED (outside W0-PR3).
- **VI-2 — executor.** `executor` is the internal identity of the server executor from the system tool registry (G1: `bash`, `system-tools.ts:598`), compared by exact equality. The following do not qualify: a name that merely contains "bash" (`my_bash_like_tool`), an MCP/plugin tool of the same name, a call to an external agent (Claude Code/Codex/Hermes) and a background call (`run_in_background:true`).
- **VI-3 — argv.** The command the executor actually received (the server record of the call) is taken, without leading and trailing spaces. It may contain only the ASCII characters `A–Z a–z 0–9 . _ / : = @ + , -` and single spaces. It is split on spaces into `argv[]`, which must be **exactly equal** to the `argv[]` of one approved validator. Any other character (quotes, `;`, `&`, `|`, `<`, `>`, `$`, `` ` ``, `(`, `)`, `%`, `^`, `!`, `*`, `?`, `~`, tab, newline) or an extra/missing argument means the call is not a validator. This is a list of allowed characters and a token comparison, not shell parsing.
- **VI-4 — cwd.** `cwd` is the path the executor actually used and must be the root of the workspace bound to the run (the run's `workspaceId`). A different `cwd` → the call is not a validator.
- **VI-5 — exit.** `exitCode` comes from the process metadata (`system-tools-helpers.ts:732-735`), never from the output text: `Exit code: 0` or "All tests passed" in stdout are not evidence. PASS requires `exitCode === 0`, `timedOut === false` and `executorError === null`.
- **VI-6 — result.** For `resultFormat:'exit_code'` VI-5 is sufficient. A validator with a declared parser (DEFERRED until after G1) additionally requires successful parsing, `failed === 0` and `total > 0`; otherwise the outcome is FAIL.
- **VI-7 — freshness.** Only qualified calls after the last observed call that can modify files in the same phase attempt count (`write_file`, `edit_file` or any `bash` call that is not a qualified validator). An earlier qualified call is stale.
- **VI-8 — test/build gate verdict** (`GateOutcome.verdict`, FRD-05.9 R3; in G1 `GateResult.passed` + `reason`):
  - `PASS`: there is at least one fresh qualified call and every fresh qualified call satisfies VI-5 and VI-6.
  - `FAIL` (`validator_failed`): a fresh qualified call with `exitCode ≠ 0`, `timedOut`, `executorError` or a failed parser.
  - `FAIL` (`validator_not_observed`): there is no fresh qualified call. This covers only rejected calls, only a self-reported claim, and a stale call. The rule applies in **every** mode, including `normal` (exception to the transitional rule FRD-02.2). Rejected calls go into `warnings[]` with the reason `validator_command_rejected:<executor|argv|cwd|background>`.
  - `NOT_RUN` (`validator_unavailable`): a qualified call did not start the validator (process start error, exit 127 from `/bin/sh` or 9009 from `cmd.exe`) → FRD-05.9 N5/S5/B5.
  - The run outcome is then determined exclusively by FRD-05.9. In G1 (before `ProofReceipt`, W1-PR7) every non-PASS yields `passed:false`, and the reason remains in `reason`.
- **VI-9 — regex is only a hint.** A command pattern (e.g. `/(npm|pnpm|yarn)\s+(test|run\s+test)|vitest|jest|tsc|pytest|cargo test/`) may serve only as a preliminary filter for a UI message or `warnings[]` ("the command looks like a test, but is not an approved validator"). It never enters `GateOutcome.verdict`, `ProofReceipt`, the trace outcome or an eval positive.

What this contract does not prove: that the project test script correctly reports failure when the validator has no result parser (e.g. `"test": "vitest || true"` in `package.json` returns 0); test coverage; code correctness. It proves only that the server executed an approved command at the workspace root after the last modification and observed its exit code.

### FRD-05.9 — Outcome table: mode × gate class × verdict — PROPOSAL (H-07, 30.09.2026) + PROPOSAL — BRIEF DIRECTION (brief §6.1, §7.2; DIR-03/07/08)

PRD-06-01, PRD-06-03, PRD-06-04, FRD-02.2, FRD-02.6, FRD-05.1, FRD-05.5, FRD-05.6, ADR-01-O3/O4/O6/O9, AT-01 and AT-03 are derived from it. Where the text differs, this table prevails. **Rules:**
- **R1 — `work` only.** `interaction:'conversation'` has no `mode`, gates or `ProofReceipt` (ADR-01-O1). It does not claim verification, and the D3 disclosure remains. Benchmark branches without a Waggle recipe (B0, B0-chat, W−recipe) have no Waggle `ProofReceipt`; they are scored only by the independent scorer.
- **R2 — gate class.** The recipe version (`HarnessRecipeVersion.invariants.mandatoryGates`, FRD-02.11) determines which gates are mandatory; the others are optional. Every gate belongs to one level: `structural` | `defined_elements` | `content_review` (FRD-05.4). In `strict` and `benchmark` the verify phase and the recipe's evidence minimum are always mandatory. No run option, env (`WAGGLE_AUTO_VERIFY`), ablation flag (A25) or `conditionalPolicy` can move them to optional. In `normal` the only permitted move is an explicit verify opt-out (R5).
- **R3 — gate verdict.** `GateOutcome { gateId, class: 'mandatory'|'optional', level, criterionIds[], verdict: 'PASS'|'CONDITIONAL'|'FAIL'|'NOT_RUN', reason?, evidenceRefs[] }`. A missing or invalid `VERDICT` = `FAIL`. `NOT_RUN` = the gate was not executed (opt-out, budget stop, process crash, unavailable validator or capability). The evidence for the verdict is server-observed (FRD-05.3). Self-reported evidence (`selfReported:true`): (a) in `strict`/`benchmark` yields `FAIL` for every gate (S4, B4); (b) on a test/build gate yields `FAIL` (`validator_not_observed`) in every mode, including `normal` (FRD-05.2 "Validator invocation"; N4); (c) the only exception is the transitional rule of FRD-02.2: in `work · normal` a gate that is not a test/build gate accepts it as evidence with `selfReported:true` in the state, and the outcome is determined by the gate verdict per rows N1–N8. This is the only rule for self-reported evidence; the PRD, ADR-01 and AT-01 adopt it verbatim.
- **R4 — CONDITIONAL that satisfies the mandatory criterion.** A `CONDITIONAL` on a mandatory gate satisfies the mandatory criterion **only** when every `unresolved[]` item is structurally bound (`criterionId` from the recipe version) to a criterion that the recipe lists as optional. The server then records the mandatory gate as `PASS`, and the limitations as an optional gate with `CONDITIONAL`. An unstructured `CONDITIONAL`, one without a link to a criterion, or an item that affects a mandatory criterion means "does not satisfy" (fail-closed).
- **R5 — verify opt-out.** Only in `work · normal`, only explicitly: a recipe field or run option with a reason, and transitionally `WAGGLE_AUTO_VERIFY==='0'`. `PhaseAttempt.endReason:'skipped_by_policy'` is recorded, `harness:phase:skipped` is emitted, and the verify gate is recorded as an optional `NOT_RUN`. In `strict`/`benchmark` the opt-out does not apply: verify is executed, and the rejected request goes into `warnings[]` and a `RunEvent`. A skip without an explicit opt-out is an error and is treated as a mandatory `NOT_RUN`.
- **R6 — overall `ProofReceipt.verdict`**, the first rule that applies is used: (1) some mandatory `FAIL` → `FAIL`; (2) some mandatory `NOT_RUN` → `NOT_RUN`; (3) some mandatory `CONDITIONAL` → `CONDITIONAL`; (4) some optional `NOT_RUN` → `NOT_RUN`; (5) some optional `CONDITIONAL` or `FAIL` → `CONDITIONAL`; (6) otherwise `PASS`. Mandatory non-`PASS` gates and `CONDITIONAL` items go into `unresolved[]`, and optional non-`PASS` gates into `warnings[]`.
- **R7 — `ProofReceipt.level`** is the highest level L for which: all mandatory gates at levels ≤ L have `PASS`, and at level L there is at least one executed gate with `PASS`. If no such level exists, `level` is `null`. If a mandatory gate of level X does not have `PASS`, `level` is strictly lower than X or `null`. A skipped verify does not raise the level.
- **R8 — trace and eval.** `TraceOutcome 'verified'` exists only with `ProofReceipt.verdict:'PASS'` and `level ∈ {defined_elements, content_review}`. A receipt with `CONDITIONAL`, `NOT_RUN` or `FAIL` never yields `verified` or an eval positive.
- **R9 — outcome names (not new states; the states are from FRD-04.1).** **COMPLETED** = `status:'COMPLETED'` + `verdict:'PASS'`. **COMPLETED with warnings** = `status:'COMPLETED'` + `verdict ∈ {CONDITIONAL, NOT_RUN}` + a non-empty `warnings[]` or `unresolved[]`. The UX label is "Completed with limitations", and "Completed (verify skipped)" only in the R5 case; never "fully confirmed". **INCOMPLETE** = every existing state that is not `COMPLETED`: `BLOCKED_APPROVAL`, `BLOCKED_CAPABILITY`, `FAILED_RETRYABLE`, `FAILED_FINAL`, `CANCELLED`. The partial artifact remains available with the label "unconfirmed draft".
- **R10 — taking over the draft.** The user may take over a labeled draft after a mandatory `FAIL` or `NOT_RUN`, and in `strict` also after a `CONDITIONAL` that does not satisfy the mandatory criterion. This never moves the run to `COMPLETED`. The run stays in its current state until the user resumes it (supplement or additional budget, new `attemptNo`) or cancels it (`CANCELLED`, artifacts retained, FRD-04.4). The only path to `COMPLETED` after a mandatory `CONDITIONAL` that does not satisfy the criterion is row N3 (`work · normal`).
- **R11 — benchmark.** Outcomes are the same as in `strict` (the same production semantics). The adapter gives no additional budget, approval or user review, so INCOMPLETE states are not resumed. The manifest (`BP-MAN-08`) records the `mode`, all `GateOutcome` records, the receipt and the status found at timeout expiry; an unfinished run is not counted as finished. The independent scorer scores the output separately from the Waggle status.
- **R12 — retry and combination.** Before an outcome from the table, that gate's `maxRetries` is exhausted (FRD-05.5); retry does not relax the gate or D3 (ADR-01-O3). When a run has several gates, the run outcome is the worst row that applies to any of its gates, in the order INCOMPLETE > COMPLETED with warnings > COMPLETED; `ProofReceipt.verdict` is computed per R6.
