## 1. Definition and boundary

### 1.1 What Waggle is

**PRD-01-01 · DECISION (D-01, D-04, D-05, D-06).** Waggle is a free, open-source, desktop-first and local-first AI work partner for the **individual**. Its primary job is knowledge work: research, analysis and business artifacts (D-06). Coding is a supported kind of work, not the product's identity. Windows/Tauri is the primary platform; CLI and web/self-host are supported, separate installation paths; cloud convenience is a later phase (D-04). BYOK stays: local-first is not a prohibition of a voluntarily chosen external model or online connector, but the product must show where data goes (D-05).

**PRD-01-02 · DECISION (D-02, D-03).** There is no separate Waggle Team or Waggle Enterprise product. Team and organizational capabilities (shared memory, governance, RBAC, policy, shared models, SLA) come from connecting to **KVARK**, which remains **exclusively on-prem**. In KVARK mode, model calls, evaluation and organizational context must not end up at a cloud provider; there is no cloud fallback.

**PRD-01-03 · CONFIRMED AT REVISION (code state vs decision).** The code at `2af0904d` still enforces the 4-tier model TRIAL/FREE/TEAMS/ENTERPRISE with a paid TEAMS: `packages/shared/src/tiers.ts:20` (`TIERS = ['TRIAL','FREE','TEAMS','ENTERPRISE']`), `:8-12` price $49/seat; `requireTier('TEAMS')` at `packages/server/src/local/routes/cost.ts:210,272`; Approvals hidden from navigation below TEAMS (`apps/web/src/lib/dock-tiers.ts:82`, `apps/web/src/components/os/AppShell.tsx:727-728`, `apps/web/src/lib/command-catalog.ts:89`); www copy "$49/seat/month" (`apps/www/messages/en.json:227-228`); Stripe checkout only for TEAMS (`packages/server/src/stripe/checkout.ts:34-37`) [F-TK-01..06]. This is a **gap between the decision and the code that the plan must close by migration** (§13), not a reason to reopen the decision.

## 6. Harness and execution modes

### 6.1 Interaction type × mode

**PRD-06-01 · Contract PROPOSAL (DIR-03; A4 "ACCEPT/REFINE").** Separate the **interaction type** (`conversation` | `work`) from the **execution mode** (`normal` | `strict` | `benchmark`). A greeting, a short clarification or a small answer does not go through the multi-phase research workflow. Detected work gets a run and a procedure. A misclassification must be visible and correctable, without silently launching expensive long-running work.

| Mode | Behavior | Invariant rules |
|---|---|---|
| Normal conversation | Existing lightweight agent flow; retrieval and permitted tools as needed. | Does not fabricate verification; scope, egress, approvals and the actual budget apply. |
| Normal work | Selected shorter/longer recipe; only justified phases. | The mandatory gates of the specific task are not optional. Failed work is not presented as verified-complete. |
| Strict work | All mandatory checks; defined evidence minimum; explicit blocked/partial when evidence or budget is lacking. | No skipping verify, no self-reported tool success, no relaxing of rules after a retry. |
| Benchmark | The same production semantics of the tested configuration, locked manifest, selected ablation profile, independent grading. | Does not unlock broader data/tools/approvals. The full Waggle configuration does not skip the mandatory verify. |

**PRD-06-02 · PROPOSAL.** The default for everyday chat = `conversation` + the existing flow; `work` is entered via detection or explicitly. The latency budget is **measured per task shape** and proposed from measurements; the earlier general "ten minutes" target is not evidence (brief §6.1). This is the "Thresholds/modes" item in §17.

### 6.2 Three evidence levels instead of a single `verified`

**PRD-06-03 · Contract PROPOSAL (brief §7.2).**

| Level | Valid confirmation | What this does not confirm |
|---|---|---|
| Execution/structural (`gate_passed`) | The file exists and parses; the sections exist; the tool finished with an **observed** status. | Correctness of the conclusions. |
| Check of defined elements | Amounts, dates, quotes, references match the marked sources; formula/test checked by the appropriate validator. | All interpretations of the sources; the business recommendation. |
| Substantive review | Rubric for completeness, fidelity to source and conclusions reviewed; explicit uncertainties remain. | Mathematical guarantee; regulatory approval. |

`VERDICT: CONDITIONAL` is neither an unconditional success nor an automatic `FAIL`: the recipe defines whether it requires supplementation, a user review, or allows a result with a stated limitation. In strict mode a mandatory gate that did not pass **blocks** `COMPLETED`; a partial artifact remains available without the "fully confirmed" label.

**PRD-06-04 · PROPOSAL (DIR-08).** A budget stop does not create success: when there are no resources for a mandatory check, the system keeps evidence of what was completed and why it is incomplete; the user may approve additional budget or accept a labeled draft; the gate is not deleted retroactively.
