Dominant pattern: the file has two error-handling generations — the boundaries Phase 2 touched (270, 314, 1746-1765, 1807/1821, 2898) catch a typed error, log with an operation tag and an id, and degrade to a stable code, while the prompt-assembly, trust, governance, tracing and post-commit tails use bare `catch {}` with a one-line why-comment and no log, so a corrupt profile, a failed trust assessment, a governance fetch bug, or a trace-store fault changes what the user or the evolution dataset sees with zero server trace. Two of those swallows sit on security boundaries and fail open (3650 leaves `approvalClass` absent against the invariant at 3635-3640; 4033 turns programming errors into "allow all"). The outer catch never logs the original error on the pre-commit path but forwards any unmatched `err.message` verbatim to the client at 5820, and that passthrough is itself pinned for three messages, so the typed-error rework must be a deliberate behavior commit, not a cleanup.
