## 2. What to ADD (only justified items)

**Release and migration**
- A1. **A release and receipt clause per wave.** List which waves touch covered runtime surfaces (chat, memory, routing, persona, provider, tool-context) and group them into as few candidate freezes as possible. Each freeze costs about 3-4 days of evidence: installer 64/64, router, 30-result persona set, 3 auth canaries, plus a crash-injection receipt.
- A2. **Data migration section:**
  - `agent-runs.json` goes to the new `runs.db`.
  - Cron leases and Loop cross-tick state (currently in personal `.mind` and Awareness) go to `runs.db`. Schedule definitions may stay.
  - Tier state in `config.json` and live TEAMS subscribers go through a Stripe freeze or migration.
  - Persona and behavioral-spec overrides need an active-version pointer.
  - Existing harness `verified` trace rows go to quarantine.
  - Each migration gets a schema version plus a documented rollback.
- A3. **GDPR/Art.17 coverage of the new stores.** `runs.db` checkpoints, artifacts and WorkItems contain user and third-party content. They must join erasure, export and `erased_subjects`/`stableHarvestId`. This is missing entirely today.

**Execution correctness**
- A4. **ExecutionMode table** (normal | strict | benchmark). It should say what each mode forbids: skipping verify, self-reported evidence, relaxing D3 after one retry, accepting a result at the budget stop. It should also give the **default for everyday chat** and its latency budget.
- A5. **Server-observed evidence.** Gates read the tool-executor ledger, never the model-supplied `phase_output.tool_calls`. Verify gates check the verdict *value* and the exit code. A FAIL result goes to retry or block.
- A6. **Phase is the atomic unit.** An incomplete phase restarts from its beginning using persisted prior outputs. No resume in the middle of an agent loop.
- A7. **ToolCallJournal / idempotency keys** (runId+phaseId+attempt+callIndex) for side-effecting tools, so a resume never sends the same email twice. Reuse the held-action idempotency pattern.
- A8. **Store decision.** A separate SQLite `runs.db` (better-sqlite3 already ships). `AgentRunRegistry` becomes an adapter over it. Needs retention/GC limits.
- A9. **Detach/reattach contract.** Explicit "continue in background"; `GET /api/runs/:id/stream?sinceSeq=`. Stop means cancel, not socket close. The socket-close-aborts behavior is deliberate today (R3-008).
- A10. **Budget persistence in checkpoints**, so a resumed run respects its token/cost budget.
- A11. **Work Progress event contract:** `{runId, phaseId, label, status, evidenceRefs}` on a per-run bus. The global `harnessEvents` emitter has no run IDs today.

**Security and privacy**
- A12. **Capability precedence envelope:** governance blockedTools > tier > persona allowlist/isReadOnly > user policy > resolver. "Mount silently" applies only inside that envelope.
- A13. **Prompt injection from harvested content.**
  - `scanForInjection` runs on ingestion.
  - Harvested items are tainted by provenance.
  - Convert-to-work from a harvested item can never trigger an external action without approval.
  - The hook read path also runs the scan and excludes `temporary`.
- A14. **Threat-model update** for inline installs (MCP binaries), plus a test proving no secrets in prompts or traces.
- A15. **Approvals are core for individuals:**
  - remove the TEAMS gate;
  - persisted BLOCKED_APPROVAL;
  - approval expiry and decline semantics;
  - approve/deny from IM channels (replace `APPROVAL_NEEDED_REPLY`).
- A16. **Evolution privacy and cost:**
  - Default to a local evaluator.
  - A cloud judge requires per-run consent plus the mandatory secret scan (`EvalDatasetBuilder.build()` is bypassed today).
  - Show a pre-run cost estimate, enforce a hard cap, and support abort.

**Evaluation and learning governance**
- A17. **Eval dataset governance:**
  - frozen holdout (≥30) plus a dataset hash;
  - an outcome taxonomy that separates `gate_passed` from `verified` (ProofReceipt-backed);
  - wire `markCorrected`, and add an explicit acceptance signal;
  - persona-scoped mining;
  - never use correction text as gold output.
- A18. **Promotion policy object.** Paired re-score of baseline and winner on the same holdout; bootstrap CI lower bound > 0; per-shape regression floor; cost/latency ceiling. Persist it in `HarnessRecipeVersion`. Fix the mismatched-sample delta (`evolution-orchestrator.ts:183-190`).
- A19. **Evolution executor ≠ judge.** Execute through the target provider router with the composed system prompt. The judge comes from a different model family.

**Models and UX**
- A20. **Model readiness contract.** A live generation probe against the selected default model. No count-based or "transient" pass (`useHasWorkingModel.ts:174,244` are false positives today).
- A21. **Hardware tier ladder:** model, quant, runtime and expected latency per band, plus a fallback when the reference model doesn't fit. Streaming, resumable pulls (today `stream:false` with a 45-minute timeout).
- A22. **Failure UX:** what the user sees for FAILED_RETRYABLE, FAILED_FINAL, BLOCKED_* and interrupted runs; notification policy; "View work" covers failures too.
- A23. **UX copy lint gate:** zero occurrences of "agent/MCP/harness/swarm" on the Essential-tier default path. One Advanced/Developer switch replaces both the experience tier and the Developer Mode toggle.
- A24. **Accessibility:** WCAG 2.2 AA for new surfaces. Work Progress uses `aria-live`, and 29 files already use it. **i18n:** the app has no i18n framework. State explicitly that 1.0 is English-only, and require new strings to be centralised so i18n is cheap later.

**Benchmarks and OSS**
- A25. **Benchmark statistics contract:**
  - pre-registration, power analysis and stratified sampling;
  - paired McNemar/TOST;
  - a fresh judge OUT_TAG per run;
  - pinned answers plus an offline recount;
  - a contamination firewall;
  - benchmark mode **runs through the production sidecar path**, not stub-core;
  - ablation flags cannot disable strict verification.
- A26. **Context specifics:**
  - token budget per model tier with a priority order;
  - trust labels from `frame.source`;
  - a hook-precedence marker (`WAGGLE_CONTEXT_INJECTED`);
  - a LoCoMo same-judge regression gate before merge.
  - Also fix the leak where workspace run summaries are copied into the personal mind (`external-tool-runs.ts:964-976`), which breaks the mind-isolation rule.
- A27. **Explicit KVARK connect FR:** a UI and route that write `kvark:connection`, and wiring of `createKvarkTools`, which has zero callers today. Gate KVARK features on a live connection, not on the ENTERPRISE tier.
- A28. **SBOM plus aggregated THIRD_PARTY_NOTICES**, checked by `certify-windows-installer.ps1`. Native binaries (onnxruntime, sqlite-vec) currently ship without license text. Model weights and the Ollama runtime go in the provenance inventory. Make the CI audit blocking; it is `continue-on-error` today.
- A29. **Pricing-table provenance.** `cost-tracker.ts:28` Opus 4.8 at $15/$75 conflicts with the $5/$25 on the benchmark branch. Verify against the official source before publishing any cost claim.

## 5. Critical path and sequencing relative to the Windows Solo launch

**Facts that drive the decision:**
1. main is 618 commits and 360 runtime files past the certified candidate. Public GO needs a fresh installer, router, persona and auth cycle *anyway*, plus Authenticode and Deep Security (both external), plus a licensing and publication path (attestation and publish are disabled while the repo is private).
2. Every PRD wave from 1 to 7 touches covered runtime surfaces. Landing any of them before a freeze resets evidence.
3. Critical dependency chain: **W0 → W1 (store, executor, ProofReceipt) → W3 (router, KW v2) → W4 (blocked resume) → W5 Work Progress wiring → W8 freeze.**
   - W2 can start in parallel with W1: extract the ContextBuilder first, then link the checkpoint after W1's store contract exists.
   - W3e starts after W0. Its "verified" definition needs the W1 ProofReceipt.
   - W5 nav/Memory IA, W6, WB and the OSS gate are independent from day 1.
   - W7 sync engines are independent; convert-to-work needs W1.

**Options:**
- **A. Ship first, then PRD (recommended).**
  - Freeze current main plus the W0 *honesty fixes* (2-4 AI-days). Fresh evidence is required regardless, so bundling them costs almost nothing extra in evidence.
  - Also bundle the cheap individual-user unblockers if the founder decides WB now: Approvals not TEAMS-gated, per-workspace cost view, session cap.
  - Run one evidence cycle and close Authenticode and Deep Security. Publish as **Waggle Solo 1.0** (installer 0.x→1.0). The PRD then becomes **Waggle 2.0** (or 1.1 as the file name says).
  - Pros: users and feedback 3-5 months earlier; the evidence machinery gets exercised once on a stable base; no evidence churn during the big refactor.
  - Cons: the public product has known limits (no durable runs, advisory harness). Those are acceptable if marketing makes no strict-verification or "frontier-class" claims.
- **B. Rebase the launch onto the PRD.** No public release until the PRD is done, about 4-6 months out. The evidence cycle is re-run 2-3 times anyway. High risk: a long stretch with no users, and the Authenticode/Deep Security pipeline stays unexercised until the end.
- **C. Hybrid internal pilot.** Keep the pilot internal and land W0+W1+W2 (about 5-7 weeks) before a public release. This makes sense only if the founder considers "strict verification + durable runs + central memory" the minimum public story.

**Recommendation: A.** Run the launch-evidence track (about 1-3 weeks, bounded by external signing and security) in parallel with the W0 audit, the OSS/licensing work and WB decisions. After GO, start W1 on main.
