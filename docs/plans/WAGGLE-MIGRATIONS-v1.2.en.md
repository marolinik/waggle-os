## 2. Shared migration contract — MIG-00

Applies to every row in §3. Status of the whole section: **PROPOSAL** (a contract proposal for FRD v1.2 and ADR (2)), except for the cited existing patterns, which are CONFIRMED AT REVISION.

### MIG-00.1 Schema version
- Every durable store gets an explicit, readable version: SQLite `meta(key='schema_version:<store>')` per store (not the global `SCHEMA_VERSION='1'`, which is informational, `schema.ts:1-8`), JSON files `{"version": N}` (pattern `agent-run-registry.ts:522-523`). The version is checked on open; an unknown higher version = **fail-closed read-only** (not a "silently empty store" as `load()` does today `:522-535`, refute F-DUR-02).
- The runtime accepts versions `[N-1, N]` during one release cycle (read-compatible), so that a code downgrade is possible without data conversion.

### MIG-00.2 Dry-run
- Every migration has a `--dry-run` that produces a report (JSON + readable text): row count per mapping class, rows it does not know how to map, estimated disk, conflicts, a list of erased/revoked items that will **not** be carried over. The dry-run writes nothing except the report to `<dataDir>/migrations/<MIG-ID>/<timestamp>/dry-run.json`.
- A dry-run is mandatory before every real pass on a user's `dataDir`; its output goes into the receipt.

### MIG-00.3 Snapshot / backup
- Before writing: a copy of the affected files in `<dataDir>/migrations/<MIG-ID>/<timestamp>/snapshot/` (SQLite: `VACUUM INTO` or the `backup()` API; JSON: a copy). The snapshot carries a `manifest.json` with the SHA-256 of every file, the code SHA, the before/after version and an **export of the Art.17/revocation ledger** (§4, GDPR-H-04) so that rollback can reapply it. **G1 exception (DP-0.09):** for the G1 mutations MIG-04(A) (W0-PR6) and MIG-05(i) (W0-PR18) the manifest exports only the existing `erased_subjects` ledger, because the revocation ledger (`revocations.json`, GDPR-H-05) comes into existence only in W1-PR15 (G2); from G2 on the export carries both.
- The snapshot has a retention (PROPOSAL: 30 days or the last 3) and is included in the E1 wipe (it must be under `dataDir`).
- Windows: use the existing rename-retry pattern (`webhook.ts:25-46`; `agent-run-registry.ts:548-573`); do not introduce a third variant.

### MIG-00.4 Mapping
- The mapping is a table in the code **and** in the document (§3 rows), with three classes: `1:1`, `derived` (derived with a recorded reason), `unmapped` (stays in the legacy column/file, is not deleted). No mapping may turn an unconfirmed state into a confirmed one (e.g. `interrupted → COMPLETED` prohibited, brief §6.4; `verified → verified` without qualification prohibited, brief §7.3).

### MIG-00.5 Idempotency
- A meta-sentinel per migration (pattern `erased_subjects_backfilled`, `db.ts:443-455`) + a repeated pass = no-op with the same receipt hash. A partially executed migration (crash) must be resumable: steps are transactions, JSON replacements are tmp+rename.

### MIG-00.6 Rollback — two classes (DIR-21)
- **Class A (code downgrade, no data restore):** data stays in the new version, the old code reads it read-compatibly (MIG-00.1). Preferred; does not touch erasure/revocation.
- **Class B (data restore from a snapshot):** allowed only when Class A is not possible. **Mandatory:** after the restore, reapply (1) the `erased_subjects` ledger (`INSERT OR IGNORE` from the manifest export) and re-run `eraseBySourceRef` for every subject that was erased *after* the snapshot; (2) vault deletions and grant revocations made after the snapshot; (3) prohibit restoring files that carry external effects as "unknown" (a sent email is not rollback-able: `pending_actions.status='executed'` stays `executed`; it must not be reverted to `approved`). The rollback receipt states what was deliberately **not** restored.
- No rollback restores a `.bak` override as the "active version" without an explicit active-pointer write (MIG-03).

### MIG-00.7 Testing on copies in an isolated `WAGGLE_DATA_DIR`
- All migrations are tested exclusively on copies in a temporary `WAGGLE_DATA_DIR` (resolution `option > env > ~/.waggle`, `packages/server/src/local/service.ts:112-121`, CONFIRMED AT REVISION). Never against the development machine's `~/.waggle`.
- Addendum 1.2.1 (H-05; the authoritative rule is the "Safe test profile (BTP)" item in [SAFE-IMPLEMENTATION-CHECKLIST](SAFE-IMPLEMENTATION-CHECKLIST.en.md)): at `2af0904d`, `WAGGLE_DATA_DIR` does not cover all writes — `routes/documents.ts:37` and `routes/pins.ts:32` build the path from `os.homedir()/.waggle`, and so do `MarketplaceInstaller`, `SecurityGate` and `tool-manifest-loader.ts:141` (CONFIRMED AT REVISION by reading the code; runtime not reproduced).
